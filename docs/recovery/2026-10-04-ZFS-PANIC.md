# 2026-10-04 22:59: kernel panic in ZFS (suspected bad RAM)

## Symptoms

During Checkpoint 8 prep the machine went down and came back at 23:02. The last commands were
lowering the ZFS ARC limit to 8 GiB, `update-initramfs -u`, and a recursive `setfacl` on
`/tank1tb/Pictures` (adding Nextcloud permissions). A Windows copy into the shares was running.

## Evidence

Journal of boot -1 ends at 22:59:54. The EFI pstore dump (`/var/lib/systemd/pstore/1791169198/`)
has the rest:

```text
[11488.742827] BUG: Bad page state in process arc_evict  pfn:2bcb91
[11488.742841] memcg:10000000000
[11488.742850] page dumped because: page still charged to cgroup
               ... abd_free_chunks / arc_hdr_free_abd / arc_evict_state [zfs]
[11492.502658] BUG: unable to handle page fault for address: ffff81d39863d3c8
[11492.502673] CPU: 7 ... Comm: setfacl Tainted: P    B      OE
[11492.502680] RIP: 0010:nvlist_lookup_byte_array+0x1d/0xb0 [zfs]
               ... zpl_xattr_get_sa / zpl_xattr_set / zpl_set_acl_impl / vfs_set_acl
               RDI: ffff81d39863d3c0   R14: ffff89d360d5e4a8   R15: ffff89d360d5e4c8
[11492.556899] Kernel panic - not syncing: Fatal exception
```

## Diagnosis

Two unrelated kernel structures were corrupted within 4 seconds, and both bad values differ from
a valid value by exactly **one bit**:

- `memcg:10000000000` is a page's cgroup field, which must be 0 when the page is freed. The value
  is a single set bit (bit 40).
- The `setfacl` crash dereferenced `ffff81d39863d3c0`. Valid kernel pointers in the same frame
  are `ffff89d3…`. `0x89` vs `0x81` is one flipped bit (bit 43).

Random single-bit flips in different places are the signature of failing memory (non-ECC RAM
or the memory controller), not of a software bug, which corrupts in structured ways.
The ARC shrink (11.4 → 8 GiB) made ZFS walk and free gigabytes of cached pages, so it touched the
corrupted memory first; it exposed the fault, it did not cause it.

This fits the earlier history: the 2026-09-28 hard freeze (`2026-09-28-HARD-FREEZE.md`) and a
pstore Oops in Firefox (`__list_del_entry_valid_or_report`, list corruption) that night. The
22 h burn-in passed, but `memtester`/`stress-ng` only test user-space memory; the ZFS ARC lives
in kernel pages they never touch. **memtest86+ has not been run yet.**

**Root cause: probable RAM / memory controller fault. Unconfirmed until memtest86+.**

## Damage check

- `zpool status -x`: all pools healthy, no known data errors.
- `setfacl`: no file on `Pictures` or `Documents` got the new ACL (`getfacl -R | grep -c user:33` = 0);

### Pattern across all evidence

| Event | RAM | Uptime | Load |
|---|---|---|---|
| 09-28 freeze + Firefox Oops (list corruption) | 16 GB | 5.5 h | light, Ollama idle |
| 10-04 22:59 panic (two single-bit corruptions) | 16 GB | 3.2 h | light |
| 10-06 21:12 panic (single-bit pointer, idle path) | 16 GB | 4 min | **40 GB ZFS copy running** (see correction) |
| burn-in (memtester + stress-ng) | 16 GB | 22 h | 100 %: **no crash** |
| memtest86+ | 16 GB | 6 h | 100 %: **0 errors** |

Corruption happens at idle or light load and never under full load. Faulty RAM cells usually fail
memtest. Failures that only appear at idle point instead at **power-state transitions**: CPU
C-states, the memory controller and DIMMs entering power-down or self-refresh, voltage regulation at
low load (board/PSU), or marginal DIMM contacts and memory training (which fits the POST freezes).
CPU microcode is current (`0xf0`, `intel-microcode 3.20251111`); the BIOS is old
(**N51 01.70, 2018-06-19**).

**Correction (same evening):** the 21:12 panic was not at idle. At boot (21:08) the missed 03:00
syncoid run started catching up and was sending ~40.6 GB of Pictures to tank500gb when it crashed;
only the crashing core was idle. Better summary: corruption shows up during **kernel / ZFS memory
activity** (ARC, send/receive, metadata updates), never during the user-space stress tests. Power
state transitions remain a suspect, but the trigger is not "idle only". The most direct bait test
is therefore a large ZFS copy: the catch-up `syncoid-backup-tank1tb-to-tank500gb` run was repeated on two sticks
on 2026-10-06 (result below).

### Other RAM tests worth trying (web search, 2026-10-08)

- **stressapptest** (Google, `apt install stressapptest`): built because memtest86+ misses errors
  that only show under heavy CPU↔RAM traffic. Useful flags here: `-W` (more CPU-heavy copies),
  `--cc_test` (cache coherency between cores), `-f`/`-d` (file/disk I/O threads at the same time)
  and `--pause_delay 60 --pause_duration 15`, which pauses all threads periodically to cause
  **power spikes**, the idle/power-transition suspect. Runs from Linux, so the kernel stays up.
  Example: `sudo stressapptest -s 28800 -M 5000 -W --cc_test --pause_delay 60 --pause_duration 15 -f /tank1tb/sat1 -f /tank1tb/sat2`.
- **PassMark MemTest86** (free edition, not memtest86+): has a **row hammer test (test 13)**; a
  "yellow PASS" means only hard-to-provoke row hammer errors were found.
- Kernel `memtest=8` boot parameter (above): a quick second opinion with physical addresses.

### Will a BIOS update fix it? (web research, 2026-10-09)

- Latest Z240 BIOS is **N51 01.92** (installed: 01.70, 2018). The release notes found (01.74 Jan 2019,
  01.83 Mar 2022) list only security fixes, Intel ME updates and CPU microcode (01.83: `0xEC`).
  **No version found mentions memory stability, DIMM compatibility, hangs, crashes or POST.**
- The microcode part is already covered: Debian's `intel-microcode` loads `0xf0` at boot, newer than
  the BIOS's `0xEC`.
- HP forum: random BSODs/hangs on Z240s are usually traced to a DIMM or a DIMM slot (one case: a
  slot that detected the full stick at POST but failed under load). One user reported memory
  failure codes at boot *after* a BIOS update, so updating is not risk-free.
- Verdict: worth doing (security fixes, possibly newer memory init code that HP does not list), but
  not a documented fix. Do it as its own step, and only after the pair-A baseline, so a change in
  crash rate can be pinned on one thing.
- Community search (HP forum, AnandTech, Arch forums, Reddit, StackExchange): no Z240 thread with this
  exact pattern, and no Reddit hits at all. Closest matches: "unstable with 4 sticks, stable with 2,
  every stick tests fine" is a common generic pattern (more load on the memory controller; one
  case was an overheating chipset); and an Arch case of idle-only panics with memtest clean, fixed
  by a power-management kernel parameter, which supports trying `intel_idle.max_cstate=1` here.
  All four DIMMs here are Kingston single-rank, 1.2 V, 2133 MT/s.
